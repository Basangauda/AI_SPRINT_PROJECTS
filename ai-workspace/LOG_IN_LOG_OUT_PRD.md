# Log In / Log Out / Register - Technical PRD

## Overview/Problem

The Quiz Maker application will be used by multiple teachers who need individual accounts before they can collaborate on a shared test bank. Today there is no way to identify who is using the application, no place to store teacher profiles, and no entry point for authenticated users to reach future quiz-building features. Teachers cannot register, sign in, or sign out, which blocks all downstream work on MCQ creation and collaboration.

---

## Hypothesis

We believe that providing simple email-and-password registration, login, and logout will give teachers a reliable way to access the application and establish the user foundation needed for collaborative test-bank work in later sprints.

---

## Scope

### In Scope

- **User table** in Cloudflare D1 with: user ID, first name, last name, username, email, group, and hashed password
- **Database migration** to create the `users` table
- **UserService** backed by D1 with create, read, update, and delete methods
- **API endpoints** (POST): `/api/auth/register`, `/api/auth/login`, `/api/auth/logout`
- **Password security**: hash passwords before persisting; verify credentials on login using the stored hash (never store or return plaintext passwords)
- **UI pages**: registration, login, logout action, and a post-auth MCQ stub page
- **Post-auth redirect**: successful registration or login navigates to the MCQ stub page
- **Input validation** on all auth endpoints and forms
- **D1 setup**: create database, add `DB` binding to `wrangler.jsonc`, run typegen
- **Vitest unit test suite**: test-driven development with tests written at the start of each phase (red), then implementation until tests pass (green)

### Out of Scope

- MCQ / test-bank functionality (next sprint)
- Social login (Google, Microsoft, etc.)
- JWT or API tokens
- Session management, cookies, or persistent auth state
- Password reset or email verification
- Role-based access control beyond storing a `group` field
- Admin user management UI
- Rate limiting and CAPTCHA (consider in a later hardening sprint)

### Cut

- **Client-side password hashing before POST** — The requirement mentions hashing on the frontend for comparison. Password verification belongs on the server: the client sends credentials over HTTPS via POST; the server hashes on registration and uses a constant-time compare on login. Client-side hashing adds complexity without replacing the need for server-side verification.
- **Session-based logout** — With no sessions or cookies, logout cannot invalidate server-side state. Logout is implemented as a POST that acknowledges the request and the UI navigates to the login page. Persistent “logged-in” state is intentionally absent in this sprint.
- **Separate UserRepository layer** — UserService talks to D1 directly via a small database helper. A second abstraction layer is unnecessary at this scale.

## Technical Requirements

### Database Schema

Database binding name: `DB`  
Database name (Wrangler): `quiz-maker-db`

```sql
-- Migration: 0001_create_users_table.sql

CREATE TABLE users (
  id TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
  first_name TEXT NOT NULL,
  last_name TEXT NOT NULL,
  username TEXT NOT NULL UNIQUE,
  email TEXT NOT NULL UNIQUE,
  group_name TEXT NOT NULL,
  password_hash TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_username ON users (username);
CREATE INDEX idx_users_email ON users (email);
```

**Column notes**

| Column | Type | Notes |
|--------|------|-------|
| `id` | TEXT PK | Opaque user ID; generated by D1 |
| `first_name` | TEXT | Required |
| `last_name` | TEXT | Required |
| `username` | TEXT | Unique, used at login |
| `email` | TEXT | Unique |
| `group_name` | TEXT | Teacher group/department; column named `group_name` because `GROUP` is a SQL reserved word |
| `password_hash` | TEXT | bcrypt hash; never store plaintext |
| `created_at` / `updated_at` | DATETIME | Audit timestamps |

**User object returned to callers** must omit `password_hash`.

### API Endpoints

All auth endpoints accept and return JSON. Credentials are sent via POST as specified.

#### POST /api/auth/register

Creates a new user account.

**Request Body:**
```json
{
  "firstName": "Jane",
  "lastName": "Smith",
  "username": "jsmith",
  "email": "jane.smith@school.edu",
  "group": "Science",
  "password": "SecurePass123"
}
```

**Response:**
- Success (201): `{ "user": { "id", "firstName", "lastName", "username", "email", "group" } }`
- Error (400): Validation error — `{ "error": "...", "details": [...] }`
- Error (409): Username or email already exists — `{ "error": "Username already taken" }`
- Error (500): Server error — `{ "error": "Internal server error" }`

**Server behavior:**
1. Validate input (Zod)
2. Check username and email uniqueness
3. Hash password with bcrypt (cost factor 10)
4. Insert row via `UserService.createUser`
5. Return safe user object (no password fields)

#### POST /api/auth/login

Validates credentials. No session/token is issued.

**Request Body:**
```json
{
  "username": "jsmith",
  "password": "SecurePass123"
}
```

Login accepts **username or email** in the `username` field for convenience (document in UI as “Username or email”).

**Response:**
- Success (200): `{ "user": { "id", "firstName", "lastName", "username", "email", "group" } }`
- Error (400): Validation error
- Error (401): Invalid credentials — `{ "error": "Invalid username or password" }` (same message for unknown user and wrong password)
- Error (500): Server error

**Server behavior:**
1. Validate input
2. Look up user by username or email
3. Compare submitted password to `password_hash` with bcrypt
4. Return safe user object on match

#### POST /api/auth/logout

Acknowledges logout. No session to destroy.

**Request Body:** none (empty body acceptable)

**Response:**
- Success (200): `{ "message": "Logged out successfully" }`

**Client behavior:** After a successful response, redirect to `/login`.

### UserService

Location: `src/lib/services/user-service.ts`

| Method | Signature | Description |
|--------|-----------|-------------|
| `createUser` | `(input: CreateUserInput) => Promise<User>` | Hash password, insert row, return safe user |
| `getUserById` | `(id: string) => Promise<User \| null>` | Read by primary key |
| `getUserByUsername` | `(username: string) => Promise<UserWithHash \| null>` | For login lookup |
| `getUserByEmail` | `(email: string) => Promise<UserWithHash \| null>` | For duplicate check / login |
| `updateUser` | `(id: string, input: UpdateUserInput) => Promise<User>` | Update profile fields; re-hash password if provided |
| `deleteUser` | `(id: string) => Promise<void>` | Hard delete (soft delete cut for this sprint) |
| `listUsers` | `() => Promise<User[]>` | Optional; useful for future admin work |

Database access goes through `src/lib/db.ts`, which obtains `env.DB` via `getCloudflareContext()` from `@opennextjs/cloudflare`.

Password helpers live in `src/lib/password.ts`:
- `hashPassword(plain: string): Promise<string>`
- `verifyPassword(plain: string, hash: string): Promise<boolean>`

Use **bcryptjs** (pure JS, compatible with Workers via `nodejs_compat`).

### User Interface Requirements

Use shadcn/ui components (`Button`, `Input`, `Label`, `Field`, `Card`) and Tailwind v4 styling. Forms POST to the API routes via `fetch` from client components (auth flows need client-side redirect handling).

#### Home / Landing (`/`)

- Brief app title and description
- Links to **Register** (`/register`) and **Login** (`/login`)

#### Register Page (`/register`)

**Form fields:**

| Field | Validation |
|-------|------------|
| First name | Required, 1–100 chars |
| Last name | Required, 1–100 chars |
| Username | Required, 3–50 chars, alphanumeric + underscore |
| Email | Required, valid email format |
| Group | Required, 1–100 chars |
| Password | Required, min 8 chars |
| Confirm password | Must match password |

**Actions:**
- Submit → POST `/api/auth/register`
- On success → redirect to `/mcq` (stub)
- On error → show inline error message(s)
- Link to login page

#### Login Page (`/login`)

**Form fields:**

| Field | Validation |
|-------|------------|
| Username or email | Required |
| Password | Required |

**Actions:**
- Submit → POST `/api/auth/login`
- On success → redirect to `/mcq`
- On error → show generic “Invalid username or password”
- Link to register page

#### MCQ Stub Page (`/mcq`)

- Heading: “MCQ Test Bank” (or similar)
- Message: functionality coming in the next sprint
- Display logged-in user info from login/register response (passed via client state or URL — no session; simplest approach: store user in `sessionStorage` on successful auth for display only this sprint)
- **Log out** button → POST `/api/auth/logout`, clear `sessionStorage`, redirect to `/login`

> **Note:** Because sessions are out of scope, `/mcq` is not protected by server middleware. Anyone can navigate to the URL. Protection arrives with real session management in a future sprint.

#### Logout

Implemented as a button on `/mcq` (and optionally a dedicated `/logout` route that performs the same POST + redirect).

## Test-Driven Development Approach

Every implementation phase follows **Red → Green → Refactor**. Tests are written **first**; they fail until the phase's production code is implemented. A phase is complete only when its tests are green **and** its acceptance criteria are met.

### Vitest setup (once, at start of Phase 1)

Vitest is not installed in the starter. Install and configure before writing the first test:

```bash
npm install -D vitest @vitejs/plugin-react @testing-library/react @testing-library/user-event jsdom vite-tsconfig-paths
```

Add `vitest.config.ts` at the repo root (see `.cursor/skills/testing/SKILL.md`) and npm scripts:

```json
"test": "vitest run",
"test:watch": "vitest"
```

### TDD rules for this feature

| Rule | Detail |
|------|--------|
| Write tests first | Each phase begins by adding/updating test files; run `npm run test` and confirm new tests **fail** (red) |
| Colocate tests | `src/lib/password.ts` → `src/lib/password.test.ts`; same pattern for services, validators, routes, components |
| Mock boundaries | Mock `@opennextjs/cloudflare`, D1, and `fetch`; unit tests must not hit a real database or network |
| Assert behavior | Test observable outputs (return values, HTTP status/body, rendered text), not internal implementation |
| Cover failure paths | Validation rejections, duplicate users, wrong passwords, missing records — not just happy paths |
| Phase gate | Before moving to the next phase: `npm run test` passes for all tests introduced in prior phases |

|-------|------------|-----------------|

| 5 | Full suite + manual preview | All unit tests green; end-to-end walkthrough on Workers runtime |

### Per-phase workflow

```
1. Read phase test plan below
2. Write/update test files listed for the phase
3. Run: npm run test          → expect NEW tests to FAIL (red)
4. Implement production code until tests pass (green)
5. Refactor if needed; re-run npm run test
6. Check phase exit criteria + acceptance criteria items for this phase
7. Update phase status marker in this PRD
```

### Implementation Patterns

**D1 access (server-only):**
```typescript
import { getCloudflareContext } from "@opennextjs/cloudflare";

export function getDb() {
  const { env } = getCloudflareContext();
  return env.DB;
}
```

**Prepared statement (numbered placeholders):**
```typescript
const { results } = await db
  .prepare("SELECT id, first_name, last_name, username, email, group_name FROM users WHERE username = ?1")
  .bind(username)
  .all<UserRow>();
const user = results[0] ?? null;
```

**Safe user mapping (never expose hash):**
```typescript
function toPublicUser(row: UserRow): User {
  return {
    id: row.id,
    firstName: row.first_name,
    lastName: row.last_name,
    username: row.username,
    email: row.email,
    group: row.group_name,
  };
}
```

**Route handler pattern:**
```typescript
export async function POST(request: Request) {
  try {
    const body = await request.json();
    const parsed = registerSchema.safeParse(body);
    if (!parsed.success) {
      return Response.json({ error: "Validation failed", details: parsed.error.flatten() }, { status: 400 });
    }
    // ... service call
    return Response.json({ user }, { status: 201 });
  } catch (error) {
    console.error(error);
    return Response.json({ error: "Internal server error" }, { status: 500 });
  }
}
```

### Important Notes

- Use `npm run preview` (Workers runtime) to test D1 bindings; `npm run dev` runs on Node and may not reflect Workers behavior accurately.
- Never apply migrations to remote D1 from an agent session; local only (`--local`).
- Generic “Invalid username or password” on login prevents user enumeration.
- `group` maps to DB column `group_name` to avoid SQL reserved-word issues.
- bcrypt cost factor 10 is a reasonable default; increase if performance allows.
- UserService methods throw domain errors (e.g. `ConflictError`); route handlers map them to HTTP status codes.

## Risks and Mitigation

### Technical Risks

- **Risk:** D1 local vs remote behavior differences (e.g. `first()` inconsistency)  
  **Mitigation:** Use `.all()` and read `results[0]`; test with `npm run preview`

- **Risk:** Hollow tests that pass before implementation (false green)  
  **Mitigation:** Write tests first; confirm they fail (red) before writing production code; follow `.cursor/skills/testing/SKILL.md`

- **Risk:** bcrypt performance on Workers CPU limits  
  **Mitigation:** Use cost factor 10; monitor latency during preview testing

- **Risk:** No real auth state means `/mcq` is publicly reachable  
  **Mitigation:** Documented as intentional for this sprint; session middleware planned later

### User Experience Risks

- **Risk:** Users expect to stay logged in after refresh  
  **Mitigation:** Clear copy on MCQ stub that full session support is coming; `sessionStorage` only persists until tab close

- **Risk:** Password rules too weak or too strict  
  **Mitigation:** Start with min 8 characters; tighten in a hardening sprint if needed

## Troubleshooting Guide

_(Populate during implementation.)_

### D1 binding undefined at runtime

**Problem:** `env.DB` is undefined when calling API routes  
**Cause:** D1 not configured in `wrangler.jsonc` or testing with `npm run dev` instead of preview  
**Solution:** Add binding, run `cf-typegen`, test with `npm run preview`

### Migration apply fails locally

**Problem:** `wrangler d1 migrations apply` errors  
**Cause:** Migration SQL syntax or wrong database name  
**Solution:** Verify database name matches `wrangler.jsonc`; inspect migration SQL for typos
